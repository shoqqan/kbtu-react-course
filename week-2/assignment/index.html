1 — Tasks

Each task is created with createTask(name). Its counter is a private variable inside a closure — the card can only reach it through getCount() and reset(). Loading takes a random 500–2000 ms and fails about 30% of the time.

    Notes

    • Run All starts all three tasks at once with tasks.map(t => t.run()) and waits with Promise.allSettled. The message “All tasks finished” is shown only when every promise is fulfilled or rejected.
    • Promise.all would reject as soon as the first task fails and we would lose the other results — that is why allSettled is used here.
    • Try clicking Run on one card several times: only that card's counter grows. Each createTask call created its own count.

    2 — Sequential vs Concurrent

    First the three tasks are run one after another (await task1.run(); await task2.run(); await task3.run();), then all together with Promise.allSettled(tasks.map(t => t.run())). Both totals are measured with performance.now().

    3 — Event Loop Demo

    The demo below contains synchronous console.log calls, two setTimeout timers, two Promise.resolve().then() callbacks (plus one queued inside a timer) and one async function. The prediction was written before running it.

    Demo source code 
    function eventLoopDemo(log) {
  log("1. script start");                                 // sync

  setTimeout(() => {
    log("7. timeout A");                                  // task
    Promise.resolve().then(() => log("8. microtask inside timeout A"));
  }, 0);

  setTimeout(() => log("9. timeout B"), 0);               // task

  Promise.resolve().then(() => log("4. promise 1"));      // microtask
  Promise.resolve().then(() => log("5. promise 2"));      // microtask

  async function asyncFn() {
    log("2. async start");                                // sync
    await null;                                           // ↓ microtask
    log("6. async after await");
  }
  asyncFn();

  log("3. script end");                                   // sync
}

    Predicted output

      Actual output

        Why this order? Call Stack → Microtask Queue → Task Queue → Event Loop

        1. Call Stack. eventLoopDemo() is pushed on the stack and runs top to bottom. "1. script start" prints. Both setTimeout calls hand their callbacks to the browser's timer and return at once. Both .then() callbacks go to the microtask queue. asyncFn() is called: it runs synchronously until the first await, so "2. async start" prints, and the rest of the function is scheduled as a microtask. "3. script end" prints. eventLoopDemo returns — the stack is empty.
        2. Microtask Queue. Before touching any timer, the event loop drains every microtask in order of registration: "4. promise 1", "5. promise 2", then the continuation of asyncFn → "6. async after await". The async continuation was queued last, so it prints last even though it looks "earlier" in the code.
        3. Task Queue. Now the event loop takes the first timer task: "7. timeout A" prints and a new microtask is queued from inside it.
        4. Microtasks again. After every task the microtask queue is drained before the next task, so "8. microtask inside timeout A" prints before timeout B.
        5. Next task. "9. timeout B" prints. The 0 ms delay never meant "immediately" — it meant "as soon as the stack and the microtask queue are empty".
